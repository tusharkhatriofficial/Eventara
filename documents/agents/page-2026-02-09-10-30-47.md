I took a look at the current implementation: [`EventConsumer`](https://github.com/tusharkhatriofficial/Eventara/blob/main/src/main/java/com/eventara/ingestion/kafka/EventConsumer.java) calls [`RealTimeRuleEvaluator.evaluateEvent()`](https://github.com/tusharkhatriofficial/Eventara/blob/main/src/main/java/com/eventara/rule/evaluation/RealTimeRuleEvaluator.java) for _every_ ingested event, and `evaluateEvent()` loops over _every active rule_ and (often) recomputes windowed metrics from Redis per rule. With “thousands of events/sec”, that effectively becomes `O(events * rules * buckets-in-window)` Redis work, which won’t scale no matter how much Kafka helps.

Here are the algorithmic patterns that typically fix this, in increasing order of impact:

1.  Micro-batch / debounce evaluation (best “quick win”)  
    Instead of evaluating rules on every event, evaluate on a short fixed tick (e.g. every 250ms / 1s), using the latest metrics.

-   On event ingest: set a `dirty` flag (or increment a counter).
-   A scheduled task runs every `tickMs`:
    -   if not dirty, do nothing
    -   else fetch metrics once and evaluate relevant rules, then clear dirty

This changes the load from “events drive evaluation” to “time drives evaluation” while still feeling “real-time” (sub-second alerting).

2.  Group rules by “evaluation key” + memoize metrics reads per tick  
    Even if you keep instant-ish evaluation, you can avoid recomputing the same Redis windows for many rules.

Create an `EvaluationKey` like:

-   `windowMinutes`
-   filter dimension (global vs `sourceFilter=X` vs `eventTypeFilter=Y`)
-   (optional) anything else that changes which Redis keys are read

Then per tick:

-   compute `bucket = getFilteredMetrics(key)` once
-   evaluate _all_ rules in that group against the same `bucket`

This usually cuts Redis reads by 10–100x when many rules share the same windows/filters.

3.  Rule indexing (avoid scanning all rules)  
    Right now it’s “for each event → loop all rules → check filters”. Flip it:

-   Keep indexes in memory when you refresh the rule cache:
    -   `rulesGlobal`
    -   `rulesBySource[source]`
    -   `rulesByEventType[type]`
    -   (and/or severity, if that’s a common filter)
-   On ingest (or per tick), select candidate rules from these indexes instead of scanning everything.

This helps a lot when most rules are scoped (per source / per event type).

4.  Incremental / stateful evaluation (true streaming algorithm)  
    For threshold-style rules, the most scalable approach is to maintain the rule’s state as counters/aggregates and update them incrementally as events arrive (sliding window ring buffer). Then you only do _constant work per event_, and only fire when a value crosses the threshold.

This is basically what stream processors (Kafka Streams / Flink) do well.

**Architecture direction (fits Kafka best)**

If you want this to sit cleanly in a Kafka architecture, the cleanest separation is:

-   **Ingestion service**: validates/persists events, publishes to Kafka (already), maybe updates “raw” metrics.
-   **Metrics aggregator** (Kafka Streams/Flink or a dedicated consumer): builds windowed metrics per key (global/source/type) and publishes compact “metric snapshot” events to another topic (e.g. `metrics_1s`, `metrics_10s`).
-   **Rule evaluator**: consumes metric snapshots (not raw events), evaluates rules, emits alerts.

Benefits:

-   evaluator load becomes proportional to “metrics updates” rather than “raw events”
-   horizontal scaling aligns with Kafka partitions
-   much less Redis round-tripping during evaluation

Even if you don’t bring in Streams/Flink, you can emulate this with a second consumer group + an internal “metrics tick” topic.

A couple of pragmatic notes (not “algorithms”, but they matter at high throughput):

-   `RealTimeRuleEvaluator` logs at `info` for every event and even for per-condition evaluation; that alone can crush throughput.
-   The evaluator currently calls `getMetricValue(...)` twice in the simple threshold path (duplicate line) — minor but unnecessary work on the hot path.

If you answer these, I can recommend the best “minimal change” path:

1.  Roughly how many active threshold rules do you expect (10 / 100 / 1k / 10k)?
2.  What alert latency is acceptable (100ms / 1s / 10s)?
3.  Are most rules global, or scoped by `sourceFilter` / `eventTypeFilter`?

Given **100–1k rules**, **mostly global**, and **~1s latency is fine**, the best production-grade path (with minimal architectural churn) is: **stop evaluating on every event** and instead evaluate on a **fixed 1s tick** using a **shared metrics snapshot**.

That changes the complexity from `O(events * rules * redisReads)` to roughly `O(rules / second + few redisReads / second)`.

**What I’d change (algorithmically) in Eventara**

**1) Micro-batch / tick-driven evaluation (the big win)**  
Right now [`RealTimeRuleEvaluator.evaluateEvent()`](https://github.com/tusharkhatriofficial/Eventara/blob/main/src/main/java/com/eventara/rule/evaluation/RealTimeRuleEvaluator.java) is called for _every event_ and loops all active rules.

For your constraints, flip it to:

-   On ingest (Kafka consumer): keep doing `redisMetrics.recordEvent(event)` as you do now
-   Also set a `dirty = true` flag (or increment a counter)
-   A scheduled job runs every **1000ms**:
    -   if not dirty → no-op
    -   else:
        -   load active rules once (`cachedRules` already exists)
        -   **group rules by** `(timeWindowMinutes, filterKey)`  
            since they’re _mostly global_, this is basically “group by windowMinutes”
        -   for each group:
            -   fetch metrics **once** for that window
            -   evaluate all rules in that group against the same `MetricsBucket`
        -   clear dirty

This is the simplest way to make Kafka throughput “matter” because evaluation is no longer in the hot path for every message.

**2) Memoize Redis reads per tick (especially for EVENT\_RATIO / derived metrics)**  
Inside the tick, keep a small map like:

-   `global(windowMinutes) -> MetricsBucket`
-   `eventType(eventType, windowMinutes) -> MetricsBucket` (only if any rule actually uses it)

That prevents `EVENT_RATIO` rules from repeatedly calling `getMetricsForEventType()` per rule within the same tick.

**3) Biggest hidden bottleneck: current metrics reads are expensive even if you tick**  
Even if you only evaluate once per second, right now `redisMetrics.getMetricsLastMinutes()` eventually goes through [`RedisMetricsService.aggregateBuckets()`](https://github.com/tusharkhatriofficial/Eventara/blob/main/src/main/java/com/eventara/metrics/service/RedisMetricsService.java), which calls `getBucket()` for each bucket, and `getBucket()` does things that are _very_ expensive at scale (notably `KEYS pattern` scans for `:source:*` / `:type:*`, plus pulling and sorting latency ZSET data).

For **global threshold rules**, you typically only need a small subset (events/errors/latency sum+count/min/max). So you’ll want a **fast-path global aggregation** that does _not_:

-   scan keys (`KEYS`)
-   load per-source / per-type maps
-   compute percentiles unless you actually have P50/P95/P99 rules

(Otherwise the evaluator will still be doing a lot of Redis work per tick.)

**4) Multi-instance behavior**  
You already have Redis cooldown keys (`eventara:rule:cooldown:*`). That’s good: if multiple instances tick at the same time, cooldown makes it “mostly safe”.

If you want to reduce duplicate evaluation work, add a simple Redis leader lock (e.g. `SET evaluator:leader <id> NX PX 1500`) so only one instance runs the tick.

**5) Quick throughput footgun**  
`evaluateEvent()` currently logs at `info` per event and per rule. Even with a better algorithm, that volume will crush throughput. For high-ingest paths, keep it at `debug` or sample it.

**Do you need Drools?**

Probably **not required** for what Eventara is doing today (threshold/ratio/rate-of-change on aggregated metrics).

Drools is “production-grade” when you need things like:

-   complex business rules over many fact types (joins/patterns), conflict resolution, agendas
-   sophisticated rule authoring workflows
-   lots of _shared sub-conditions_ where RETE-style incremental matching helps

But in your current model, the “facts” are basically a **metrics snapshot** (counts/rates over windows). With that input shape:

-   Drools still ends up evaluating a lot of rules per snapshot
-   it does **not** remove the need to micro-batch (you still don’t want to “fire all rules per event”)

So I’d treat Drools as an _optional future extension_ if/when you add truly general-purpose rule types (field-level predicates over event payloads, multi-entity correlation, etc.). For the current threshold rules, a purpose-built evaluator will be:

-   easier to control latency
-   easier to reason about
-   easier to optimize around Redis access patterns

Two quick questions that affect the best “fast-path metrics” design:

1.  What are the common `timeWindowMinutes` values you expect in real use (1 / 5 / 15 / 60)?
2.  Do you actually plan to alert on percentiles (P95/P99), or mostly counts/error-rate/avg-latency?

# Adaptive Rate-Based Evaluation System

## Overview

This document describes the proposed **Adaptive Rate-Based Evaluation** algorithm for Eventara's real-time rule evaluation engine. The current implementation evaluates rules on every incoming event, which creates O(events × rules × redis) complexity - unsustainable at high throughput.

The adaptive approach dynamically adjusts evaluation frequency based on incoming event rate, optimizing for both **low-latency alerting** during high traffic and **resource conservation** during idle periods.

---

## Problem Statement

### Current Architecture

```
┌──────────────────────────────────────────────────────────────────┐
│                     Current: Per-Event Evaluation                 │
├──────────────────────────────────────────────────────────────────┤
│                                                                   │
│   EventConsumer.ConsumeEvent()                                    │
│         │                                                         │
│         ▼                                                         │
│   realTimeRuleEvaluator.evaluateEvent(event)  ← Called per event │
│         │                                                         │
│         ▼                                                         │
│   for (AlertRule rule : rules) {              ← Loop 100-1k rules│
│       bucket = getFilteredMetrics(config);    ← Redis call       │
│       if (threshold crossed) fireAlert();                        │
│   }                                                              │
│                                                                   │
│   At 1000 events/sec × 500 rules = 500,000 Redis ops/sec 🔥      │
└──────────────────────────────────────────────────────────────────┘
```

### Issues

1.  **Redis Overload**: Each event triggers `O(rules)` Redis reads
2.  **Duplicate Work**: Same metrics re-fetched for every event
3.  **No Batching**: Window-based metrics don't change per-event
4.  **Wasted CPU**: Low-traffic periods still run expensive loops

---

## Proposed Solution: Adaptive Rate-Based Evaluation

### Core Concept

Instead of evaluating on every event, evaluate on a **dynamic tick interval** that adapts to the current event ingestion rate:

Event Rate (per second)

Evaluation Interval

Rationale

< 0.1 (< 5/min)

30 seconds

Idle mode - conserve resources

0.1 - 1 (5-50/min)

10 seconds

Low traffic - responsive but efficient

1 - 10 (50-500/min)

2 seconds

Medium traffic - near real-time

10 - 100 (500-5k/min)

500 milliseconds

High traffic - fast response

\> 100 (> 5k/min)

100 milliseconds

Burst mode - maximum responsiveness

### Complexity Reduction

```
┌──────────────────────────────────────────────────────────────────┐
│                  Proposed: Adaptive Tick Evaluation               │
├──────────────────────────────────────────────────────────────────┤
│                                                                   │
│   EventConsumer.ConsumeEvent()                                    │
│         │                                                         │
│         ▼                                                         │
│   eventCounter.incrementAndGet();   ← O(1) atomic operation      │
│   dirtyFlag.set(true);              ← O(1)                       │
│                                                                   │
│   ─────────────────────────────────────────────────────────────  │
│                                                                   │
│   @Scheduled (dynamic interval)                                   │
│         │                                                         │
│         ▼                                                         │
│   if (!dirty) return;               ← Skip if no new events      │
│   snapshot = captureMetricsOnce();  ← 1 Redis call per tick     │
│   for (AlertRule rule : rules) {                                 │
│       evaluateAgainstSnapshot(rule, snapshot);  ← No Redis!     │
│   }                                                              │
│   adjustInterval(eventRate);        ← Adapt for next tick       │
│                                                                   │
│   At 1000 events/sec = ~20 Redis ops/sec 🚀                     │
└──────────────────────────────────────────────────────────────────┘
```

## Implementation Design

### 1\. Event Rate Monitor

Track events per second using an atomic counter with sliding window:

@Component
public class EventRateMonitor {
    
    private final AtomicLong eventCounter = new AtomicLong(0);
    private volatile long lastSampleTime = System.currentTimeMillis();
    private volatile double currentEps = 0.0;  // Events per second
    
    // Exponential moving average factor (0.3 = 30% new, 70% old)
    private static final double EMA\_ALPHA = 0.3;
    
    /\*\*
     \* Called on every event - O(1) operation
     \*/
    public void recordEvent() {
        eventCounter.incrementAndGet();
    }
    
    /\*\*
     \* Calculate EPS and update the moving average
     \* Called periodically (e.g., every second)
     \*/
    public double sampleAndGetEps() {
        long now = System.currentTimeMillis();
        long elapsed = now - lastSampleTime;
        
        if (elapsed < 100) return currentEps; // Min sample interval
        
        long events = eventCounter.getAndSet(0);
        double instantEps = (events \* 1000.0) / elapsed;
        
        // Exponential moving average for smooth transitions
        currentEps = (EMA\_ALPHA \* instantEps) + ((1 - EMA\_ALPHA) \* currentEps);
        lastSampleTime = now;
        
        return currentEps;
    }
    
    public double getCurrentEps() {
        return currentEps;
    }
}

### 2\. Adaptive Evaluation Scheduler

Dynamic scheduling based on event rate:

@Service
@Slf4j
public class AdaptiveRuleEvaluator {
    
    private final EventRateMonitor rateMonitor;
    private final RuleRepository ruleRepository;
    private final RedisMetricsService redisMetrics;
    private final AlertTriggerHandler alertHandler;
    
    private final AtomicBoolean dirtyFlag = new AtomicBoolean(false);
    private volatile long currentIntervalMs = 10\_000; // Start at 10s
    private volatile long lastEvaluationTime = System.currentTimeMillis();
    
    // Configurable thresholds
    private final EvaluationConfig config;
    
    /\*\*
     \* Called from EventConsumer on every event - O(1)
     \*/
    public void onEventIngested() {
        rateMonitor.recordEvent();
        dirtyFlag.set(true);
    }
    
    /\*\*
     \* Scheduled check - runs frequently but does minimal work
     \*/
    @Scheduled(fixedRate = 100) // Check every 100ms
    public void checkAndEvaluate() {
        long now = System.currentTimeMillis();
        long elapsed = now - lastEvaluationTime;
        
        // Not time yet, or no new events
        if (elapsed < currentIntervalMs || !dirtyFlag.get()) {
            return;
        }
        
        // Reset and evaluate
        dirtyFlag.set(false);
        lastEvaluationTime = now;
        
        try {
            evaluateAllRules();
        } finally {
            // Adjust interval based on current event rate
            double eps = rateMonitor.sampleAndGetEps();
            currentIntervalMs = calculateInterval(eps);
            
            log.debug("Adaptive interval adjusted: EPS={}, interval={}ms", 
                      eps, currentIntervalMs);
        }
    }
    
    private void evaluateAllRules() {
        List<AlertRule\> rules = getCachedActiveRules();
        
        // Group rules by evaluation key to share Redis reads
        Map<EvaluationKey, List<AlertRule\>> ruleGroups = groupByEvaluationKey(rules);
        
        for (Map.Entry<EvaluationKey, List<AlertRule\>> entry : ruleGroups.entrySet()) {
            // ONE Redis call per group
            MetricsBucket bucket = fetchMetrics(entry.getKey());
            
            for (AlertRule rule : entry.getValue()) {
                evaluateRuleAgainstBucket(rule, bucket);
            }
        }
    }
    
    /\*\*
     \* Calculate evaluation interval based on events per second
     \*/
    private long calculateInterval(double eventsPerSecond) {
        if (eventsPerSecond < config.getIdleThreshold()) {
            return config.getIdleIntervalMs();      // 30s for idle
        }
        if (eventsPerSecond < config.getLowThreshold()) {
            return config.getLowIntervalMs();       // 10s for low
        }
        if (eventsPerSecond < config.getMediumThreshold()) {
            return config.getMediumIntervalMs();    // 2s for medium
        }
        if (eventsPerSecond < config.getHighThreshold()) {
            return config.getHighIntervalMs();      // 500ms for high
        }
        return config.getBurstIntervalMs();         // 100ms for burst
    }
}

### 4\. Rule Grouping for Metrics Sharing

Group rules by evaluation key to minimize Redis calls:

/\*\*
 \* Key that determines which rules can share the same metrics fetch
 \*/
@Value
public class EvaluationKey {
    int windowMinutes;
    List<String\> sourceFilter;    // null = global
    List<String\> eventTypeFilter; // null = all types
    
    public static EvaluationKey fromRule(AlertRule rule) {
        Map<String, Object\> config = rule.getRuleConfig();
        return new EvaluationKey(
            parseIntOrDefault(config.get("timeWindowMinutes"), 15),
            (List<String\>) config.get("sourceFilter"),
            (List<String\>) config.get("eventTypeFilter")
        );
    }
}

// Usage in evaluation
Map<EvaluationKey, List<AlertRule\>> groups = rules.stream()
    .collect(Collectors.groupingBy(EvaluationKey::fromRule));

// Result: Rules with same window+filters share ONE Redis call
// e.g., 500 rules might reduce to 20-50 unique Redis calls

The “adaptive rate-based evaluation” plan is directionally solid — it’s basically the same core win we discussed (tick-driven evaluation + shared metrics snapshot), with an extra knob to slow down during idle periods.

Given your constraints (**100–1k rules**, **mostly global**, **~1s latency acceptable**), I’d proceed in this order:

1.  **Ship a fixed tick first (e.g., 1s) + rule grouping + per-tick metrics memoization.** This removes the `O(events × rules × redis)` blow-up immediately and is much simpler to reason about.
2.  Add **adaptive intervals** only if you actually care about conserving resources at very low traffic _and_ you’re OK with higher idle latency (e.g., 10–30s).

**Why I wouldn’t start with adaptive as Phase 1**

-   The complexity/risk is mostly in **metrics fetching cost** (Redis aggregation, `KEYS`\-style scans, percentile work), not in whether the tick is 1s vs 500ms.
-   Adaptive scheduling adds failure modes (jitter, uneven sampling, “why did my alert take 27s?”) that you don’t need to solve the big scaling problem.

**Concrete improvements if you do implement the adaptive version**

-   **Avoid “poll every 100ms”** (`@Scheduled(fixedRate = 100)` + internal interval checks). It’s easy but wasteful and noisy.
    
    -   Prefer a `ScheduledExecutorService` / Spring `TaskScheduler` where you **reschedule the next run** after each evaluation based on `currentIntervalMs`.
    -   If you keep the 100ms poll, it’s still a big win vs per-event, but it’s unnecessary overhead.
-   **Don’t compute EPS only when you evaluate.**
    
    -   If you slow to 30s in idle, `sampleAndGetEps()` becomes coarse and can react late to spikes.
    -   Better: have a small sampler that runs on a fixed cadence (ex: every 1s) updating `currentEps` (EMA), and the evaluator reads it.
-   **Be careful with the `dirtyFlag` race.**
    
    -   Pattern that works well:
        -   `onEventIngested()`: increment counter (or set dirty)
        -   `tick()`: `hadEvents = dirtyFlag.getAndSet(false)` (or compare counters)
        -   if events arrive during evaluation, `dirtyFlag` becomes true again and you run next tick
-   **Leader election (multi-instance).**
    
    -   Cooldowns prevent duplicate alert spam, but you’ll still waste CPU/Redis if all instances tick.
    -   A simple Redis lock (`SET evaluator:lock <id> NX PX <interval+buffer>`) or a library like ShedLock is enough.
-   **Biggest performance lever: fast-path metrics snapshots.**
    
    -   Even with a perfect adaptive scheduler, if each tick calls the expensive path in `RedisMetricsService.aggregateBuckets()` (esp. per-source/per-type scans + percentiles), you’ll still pay a lot per tick.
    -   For “mostly global threshold rules”, implement a “global summary only” read path that avoids:
        -   scanning `:source:*` / `:type:*` keys
        -   percentile computation unless some rule actually needs it
-   **Rule grouping key should include “what metrics are needed”.**
    
    -   Not just `(windowMinutes, filters)` — also include whether the group needs percentiles, breakdowns, etc., so you don’t compute heavy metrics for rules that don’t need them.

**Decision / recommendation**

-   Yes, proceed with the tick-driven approach, but I’d start with **fixed 1s** + grouping + metrics memoization + fast-path metrics. Add adaptive later if you want idle-mode savings.

**One question to unblock the “adaptive” part**

-   When traffic is basically idle, is it acceptable for alerts to be delayed up to **10–30 seconds**, or do you want to keep the “worst-case” latency around **~1 second** at all times?
